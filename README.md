# 🧩 Capstone Project: Phishing Email Classification

## 📘 Overview
This project aims to build a **multiclass classification system** that can automatically detect and categorize phishing emails into specific threat types:
- **Benign**
- **Financial Scam**
- **Business Email Compromise (BEC)**
- **Credential Harvesting**

---

## 🧮 Dataset Summary

### **Data Source**
The dataset integrates multiple campaign collections of email data gathered for phishing research. Each record represents a single email instance and includes metadata, textual, and structural features relevant to phishing detection.

- `enron`
- `spamAssassin`
- `nazario`
- `nigerianFraud`
- `phishingPot`

### **Target Variables**
`classification` — categorical feature with the following classes:
- `benign`
- `financial_scam`
- `bec`
- `credential_harvesting`

### **Key Features**
The dataset includes both **raw** and **engineered** attributes derived from email headers, body content, and contextual groupings.  
A few representative examples:
- `subject_normalized`
- `sender_normalized`
- `body_length`
- `has_links`
- `dkim_result`
- `spf_result`
- `dmarc_result`

---

## 🧱 Schema and Data Design Improvements

Following feedback, the dataset schema was **redesigned** to support temporal, campaign-aware evaluation and mitigate data leakage risks.  
Key updates include:

### **1. Normalized Schema**
- Standardized key identifiers such as **subject**, **sender**, and **date bucket** to reduce variability.
- Aligned feature names and formats across multiple raw sources.

### **2. Handling Missingness**
- Missing values were reviewed and replaced
- Imputation will be implemented based on model performance with current dataset

### **3. Duplicate and Near-Duplicate Grouping**
- Content duplicates were removed
- Similar emails were grouped

### **4. Time-Aware and Campaign-Aware Splitting**
- Implemented data splits that respect **temporal order** and **campaign boundaries** to avoid look-alike leakage.
- This ensures the model’s evaluation reflects realistic deployment conditions.

### **5. Synthetic BEC Labeling**
- Explicitly labeled **synthetic BEC examples** to ensure sufficient representation of rare classes and support balanced training later.

---

## 🔀 Data Splitting

| Split | Proportion
|--------|-------------
| **Train** | 80% 
| **Validation** | 10% 
| **Test** | 10% 

- `random_state=42` is used to ensure reproducibility.
- Stratified by target class (`stratify=y`)
- No preprocessing or encoding was performed before this split to prevent **data leakage**.

---

## ⚙️ Planned Next Steps

### **Phase 2 — Feature Encoding**
- Apply suitable encoding methods from `sklearn.preprocessing` based on feature type (categorical, ordinal, text-derived, etc.).

### **Phase 3 — Modeling**
- Train baseline models (e.g., `XGBoost`) on encoded data.
- Evaluate with multiclass metrics (recall, precision) under k-fold cross-validation on the validation subset.

### **Phase 4 — Evaluation and Reporting**
- Compare system variants:
1. With vs. without outlier removal  
2. With vs. without feature aggregation
- Final performance to be reported on the **held-out test set**.
